# 교전 후 생존 유닛의 경로 복귀 정체 진단

- 최소 재현: 안전한 이동이 가능해도 정지한 시간이 **377틱 → 0틱**. `after-result.txt` 참조.

## 확인된 원인

`DefenseBattle.TryRejoinRoute`가 먼 복귀 지점까지 **선분 전체**의 유닛 충돌을 검사하고, `RouteBypassOffset`으로 그 지점보다 가까운 복귀 후보를 제외한다. 따라서 다른 유닛이 멀리서 합류하면 당장 한 틱 이동할 공간이 충분해도 정지한다. 이는 상대 팩션이나 살아 있는 전투 타깃이 없어도 발생한다.

1. `DefenseBattle.cs:773-791`: 가장 먼 유효 웨이포인트부터 고르고, 그곳에 도착하기 전부터 `RouteBypassOffset`을 저장한다.
2. `DefenseBattle.cs:761-778`: 다음 틱에는 저장한 offset보다 가까운 후보를 제외하고, `CanFollowRoute(enemy, waypoint)`로 먼 지점까지 검사한다. 실제 한 틱의 이동점은 이 검사 뒤 781줄에서 계산한다.
3. `CombatPositioning.cs:308-309,984-1001`: 이 검사는 같은 팩션을 포함한 모든 다른 유닛의 몸통 반경을 사용한다. 선분 어디든 유닛이 있으면 전체 이동을 거절한다.
4. `DefenseBattle.cs:675-707`: 복귀점이 벽에 가려지지 않았다면 `routeInSight=true`여서 대체 경로 탐색도 건너뛴다. 경로 밖 유닛은 일반 경로 이동으로 진행하지 못하고, 0.35초마다 양보 경로를 찾는다. 이 양보 경로도 `CombatPositioning.cs:332-333`에서 목표까지 두 선분 전체가 비어 있어야 한다.

교전·우회 뒤에는 유닛이 원래 경로에서 벗어나기 때문에 이 분기를 사용한다. 앞 유닛은 정상 경로를 따라 움직여도 뒤 유닛은 긴 구간이 완전히 비기를 기다릴 수 있다. 여러 유닛이 합류하며 해당 구간의 점유가 바뀌면 정지와 재개가 반복될 수 있다. 0.35초는 양보 재시도 주기이며, 모든 멈춤이 정확히 그 주기로 발생한다는 뜻은 아니다.

## 최소 재현 및 인과 비교

`run.ps1`은 게임의 `EnemyUnit`, `DefenseBattle`, `CombatPositioning`, `DefenseGrid` 원본을 직접 컴파일한다. Unity 자료형은 기존 `BalanceSim/UnityStubs.cs`를 사용한다. 전투 소스 복사본이나 수정본은 사용하지 않는다. NuGet 접근 없이 설치된 .NET SDK의 C# 컴파일러로 실행하며 산출물은 무시되는 `BalanceSim/obj/route-stutter-diagnosis`에 쓴다.

조건: 한 칸 통로, 반경 0.3인 같은 편 두 유닛, 이동속도 뒤 1.7/앞 1.2. 뒤 유닛을 경로에서 0.1만큼 벗어난 위치에 두고 한 틱 실행해 먼 복귀점(offset 10)을 실제 코드가 선택하게 한다. 다음 틱부터 약 4칸 앞에 같은 편 유닛을 추가해 통로 합류를 모사한다. 상대 팩션은 없으며 타깃·전투 대기열도 null이다.

| 비교 | 안전한 다음 한 틱 이동이 가능해도 정지한 틱 | 관찰 |
| --- | ---: | --- |
| 원본 동작 | 377틱 = 약 6.28초 | 앞 유닛과 거리 약 4→11칸으로 벌어져도 정지. 앞 유닛이 코어에서 제거된 뒤 재개 |
| 진단용으로 매 틱 `RouteBypassOffset=-1` | 0틱 | 가까운 복귀점이 다시 후보가 되어 연속 이동, 코어 도착 |

각 비교에 검증 조건을 넣었으며 두 조건 모두 통과했다. 출력은 `result.txt`, 재현 코드는 `Diagnosis.cs`다. **offset 초기화 비교는 원인 분리 실험이지 권장 패치가 아니다.** 무조건 초기화하면 기존에 방지하던 역주행·좌우 왕복이 다시 생길 수 있다.

실행: 저장소 루트에서 `./ai-use/evidence/20261119-route-stutter/run.ps1`.

## 수정 방향

정적 지형으로 복귀 경로를 고르는 판단과, 다음 한 틱의 동적 유닛 충돌 판단을 분리해야 한다. 가까운 안전 지점까지 전진하고 실제로 가까워졌을 때 양보하도록 하되, 복귀점 고정은 장기간 진전이 없을 때 다시 평가해야 한다. 역주행 방지·유닛 겹침 방지·결정론도 함께 검증해야 한다.

## 검증 범위와 미확인

- URP 17.0.1, Input System 1.19.0/activeInputHandler=1, uGUI 사용 확인.
- 원본 체크아웃과 이 작업 사본의 세 이동·전투 파일 SHA256 일치 확인. 원본 체크아웃 파일은 변경하지 않았다.
- Unity CLI를 실행하려 했으나 이 셸에서 `unity`를 찾지 못했다. 연결 메타데이터는 다른 체크아웃의 에디터를 가리킨다. 에디터 Play Mode와 EditMode 테스트는 실행하지 않았다.
- 최초 `dotnet run`은 사용자 NuGet 설정 접근 권한으로 실패했다. 이후 외부 패키지가 필요 없는 직접 컴파일 방식으로 성공했다.
- 스테이지 연결 정정: 초기 조사에서 테마 이름과 데이터 에셋 이름을 동일하게 간주했으나, 후속 `.meta` GUID 확인과 Unity `HandmadeStagesLoadTheirStageData` 테스트에서 GameScene 2번 GoldenMaple은 **Stage2_Temp/Waves2**, 3번 Snowfield는 **Stage3/Waves3**를 참조함을 확인했다. 따라서 3스테이지 4웨이브가 존재한다. 별도 Stage_Snowfield 에셋의 3웨이브 제한은 해당 슬롯에 적용되지 않는다.
- 사용자 판의 벽 배치·마법 입력·선택 스폰·메모리 내 에셋 상태가 없으므로 해당 두 판을 그대로 재현한 결과는 아니다. 실제 코드에서 독립 재현된 결함과 증상에 맞는 인과 경로를 확인한 것이다.
